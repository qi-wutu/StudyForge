# BM25 手写教程 — 从零实现一个搜索引擎核心

## 一句话

BM25 就是"给你一个查询，从一堆文档里找出最相关的那几篇"。

比如你搜 **"GMP 模型中 P 的作用"**，它能从十几个知识点里找出跟 GMP 相关的那些，按相关度排序。

---

## 核心公式（就一个）

```
BM25 分数 = IDF × (TF × (k1 + 1)) / (TF + k1 × (1 - b + b × 文档长度 / 平均文档长度))

对查询里的每个词算一遍分数，加起来。
```

不要怕，拆开看就三部分：

### 1. TF — 这个词在文档里出现了几次？

```
文档 A："P 是处理器，M 需要绑定 P 才能运行 G"
查询："P 的作用"

词 "P" 在文档 A 里出现了 2 次 → TF = 2
词 "的" 在文档 A 里出现了 0 次 → TF = 0（跳过，不算）
```

直觉：一个词出现越多，文档越相关。

### 2. IDF — 这个词有多"稀有"？

```
总文档数 N = 10
出现"P"的文档数 df = 3（3 篇提到了 P）
IDF = log(1 + (10 - 3 + 0.5) / (3 + 0.5)) = log(1 + 7.5/3.5) ≈ 0.87

出现"Goroutine"的文档数 df = 1（只有 1 篇提到）
IDF = log(1 + (10 - 1 + 0.5) / (1 + 0.5)) = log(1 + 9.5/1.5) ≈ 1.40
```

直觉：烂大街的词（"代码"、"语言"）IDF 低，稀有词（"work stealing"）IDF 高。

### 3. 长度归一化 — 长文档的 TF 天生高，要打折

```
文档 A 50 个字，文档 B 500 个字
词 "P" 在两篇文档里都出现 3 次 → TF 一样 → 但 B 里 3/500 明显没那么重要

k1 控制：TF 多高才算"饱和"（默认 1.5）
b 控制：长度惩罚多狠（默认 0.75，0=不惩罚，1=完全惩罚）
```

直觉：100 字里出现 3 次比 1000 字里出现 3 次重要得多。

## 代码一步步来

### 第一步：分词（jieba）

中文分词用 jieba，基于前缀词典 + HMM 模型：

```python
import jieba

def _tokenize(text: str) -> list[str]:
    return jieba.lcut(text.lower())
```

为什么不用其他方案？

- **bigram**：零依赖但精度低，"处理器"会被切成"处理"、"理器"
- **jieba**：效果更好，而且是纯 Python 库，安装简单，面试也能讲清楚它的大致原理

这里的取舍是：**BM25 核心公式自己手写，分词用成熟的库**——各自发挥优势。

### 第二步：建索引

```python
class BM25Index:
    def build(self, docs: list[str]):
        # 对每篇文档分词，记录长度
        # 统计每个词出现在几篇文档中（文档频率 DF）
        for doc in docs:
            terms = _bigram(doc)
            self.doc_lengths.append(len(terms))        # 每篇长度
            doc_term_set.append(set(terms))             # 每篇用了哪些词

        self.avg_doc_length = sum(self.doc_lengths) / len(docs)

        for terms in doc_term_set:
            for term in terms:
                self.doc_freq[term] = self.doc_freq.get(term, 0) + 1
                # 比如 "P" 出现在 3 篇文档中 → doc_freq["P"] = 3
```

### 第三步：检索

```python
def search(self, query: str, top_k: int = 5):
    query_terms = _bigram(query)         # "P的作用" → ["P的", "的作", "作用"]
    query_tf = Counter(query_terms)      # 查询里的词频

    for i, doc in enumerate(self.docs):
        score = 0.0
        dl = self.doc_lengths[i]         # 当前文档长度

        for term, qtf in query_tf.items():
            if term not in self.doc_freq:
                continue                 # 这个词在所有文档里都没出现过，跳过

            df = self.doc_freq[term]     # 出现这个词的文档数
            tf = doc_tf.get(term, 0)     # 当前文档里这个词出现几次
            if tf == 0:
                continue                 # 这篇文章没有这个词，跳过

            # === 公式来了 ===

            # 1. IDF：词越稀有，值越大
            idf = math.log(1 + (N - df + 0.5) / (df + 0.5))

            # 2. BM25 核心
            score += idf * (tf * (k1 + 1)) / (
                tf + k1 * (1 - b + b * dl / avg_dl)
            )

    # 按分数从高到低排序，返回 top_k
```

## 面试官可能会追问

### "k1 和 b 分别控制什么？"

- **k1**（默认 1.5）：词频的"饱和点"。
  - k1=0：只看 IDF，词频不重要（一个词出现 1 次和 100 次一样）
  - k1 越大：词频越重要
  - 1.2~2.0 是常见值。为什么是 1.5？经验值，大部分场景表现好

- **b**（默认 0.75）：长度归一化的力度。
  - b=0：不看文档长度，长文档天然分高
  - b=1：完全按长度惩罚
  - 0.75 是经验值

### "IDF 里的 +0.5 是干什么的？"

**平滑**。防止两种情况：
- `df = 0`（新词没出现过）：log 里会无穷大，+0.5 保底
- `df = N`（所有文档都有这个词）：IDF ≈ log(1 + 0.5/9.5) ≈ 0.05，接近 0

### "你这里用的什么平滑版本？"

BM25 有很多变体。这里用的是 BM25 的 Okapi 变体——最常用的版本，公式里的 +0.5 是 Robertson 平滑。

### "为什么不用 Elasticsearch 里的 BM25？"

因为 ES 的 BM25 实现你看不到细节。手写的每一行都是你写的，面试官追问任何一行你都能答。

## 完整流程：从查询到结果

```
查询："P 的作用"
  ↓ bigram 分词
["P的", "的作", "作用"]
  ↓
对每篇文档算 BM25 分数：

文档 A："P 是处理器，M 需要绑定 P 才能运行 G"
  TF: "P的"=0, "的作"=0, "作用"=0  → 分数 = 0

文档 B："P 的作用是调度 goroutine 到线程"
  TF: "P的"=1, "的作"=1, "作用"=1
  IDF: "P的" 稀有度高
  → 分数 = 2.92

文档 C："channel 是 Go 的通信机制"
  TF: 全部为 0  → 分数 = 0
  ↓
排序 → 文档 B 是唯一匹配的
```

## 这个 BM25 在你项目里的用途

1. **语义去重**（`planner` 节点）：提取新知识点时，跟已有知识点算 BM25 相似度，超过 0.8 就认为是重复的
2. **检索增强出题**（`question_gen` 节点）：出题时检索相关知识拼进 prompt，让题目有上下文
3. **面试素材**：面试官问 RAG，你就能从 BM25 分词讲到公式再讲到 k1/b 参数

## 为什么 BM25 比简单关键词匹配好？

| 方式 | 问题 |
|---|---|
| 简单匹配 | "Go" 匹配到 10 篇，不知道哪个最相关 |
| TF（词频） | 500 字的文章 TF 天然高，不公平 |
| TF-IDF | 没有长度归一化 |
| **BM25** | 以上问题都解决了 + 可调参（k1, b） |
