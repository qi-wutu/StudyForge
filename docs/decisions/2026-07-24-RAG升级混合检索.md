# RAG 升级：从 BM25 到 Hybrid Search（混合检索）

> 背景：纯 BM25 关键词匹配无法处理同义/近义表达，导致薄弱扩散和出题上下文质量受限。
> 选型：Hybrid Search = BM25 精确匹配 + 向量语义检索，加权融合。
> 本文记录技术选型的完整思考过程，以及面试时如何回答相关问题。

---

## 现状：纯 BM25

```
query ──→ jieba分词 ──→ 词频统计 ──→ 排序输出
```

当前 BM25 用在三个地方：

| 用途 | 位置 | 作用 |
|---|---|---|
| 知识点去重 | `planner` 节点 | BM25 阈值 0.8，避免重复提取 |
| 薄弱扩散 | `_build_review_queue` | 薄弱 KP → BM25 搜关联 KPs 加入快车道 |
| 出题上下文 | `question_gen` | 当前 KP → BM25 搜 top-3 供 LLM 参考 |

### BM25 的局限性

BM25 是词袋模型，依赖**词汇重叠**：

```
query: "goroutine 怎么被调度的"
文档:  "GMP 模型中 M 如何从 P 获取 G"

→ 共同关键词: 无（"GMP" ≠ "goroutine"，"调度" ≠ "G"）
→ BM25 得分: 0
→ 结果: 语义相关但词不匹配 → 搜不到
```

在中文八股文场景下，同一个概念有多种表述方式（"GMP 模型"、"Goroutine 调度"、"协程管理"），BM25 无法建立这种语义关联。

---

## 方案对比

### 方案 A：纯 BM25（当前方案）

**优点：**
- 零依赖，无需额外模型
- 精确命中，不会出现"不相关但向量近"的误召
- 可解释性强，分数可直接归因到关键词

**缺点：**
- 不能理解语义近义词
- 薄弱扩散 lane 质量受限——词相似但概念不相关的 KP 可能被拉进来
- 出题上下文经常为空（词不匹配）

### 方案 B：纯向量检索

```python
# 伪代码
query_vec = embed(query)              # 384维向量
best = max(docs, key=lambda d:         # 暴力余弦
    cosine_similarity(query_vec, d.vec))
```

**优点：**
- 语义匹配，"goroutine 调度" → "GMP 工作窃取"
- 不需要分词，没有 OOV（未登录词）问题

**缺点：**
- **冷启动问题**：新导入的资料没有历史 embedding
- **高频术语偏置**："GMP"、"defer" 等专有名词在高维空间中被上下文拉偏，反而不如 BM25 精确命中
- **误召风险**：语义相似的但不相关的文档（同样是"锁"，"sync.Mutex"和"分布式锁"向量可能很近）
- 需要额外维护 embedding 模型

### 方案 C：Hybrid Search（选中方案 ✅）

```
query ──→ ┌── jieba分词 ──→ BM25得分 ──┐
           │                              ├── 加权融合 ──→ 排序输出
           └── embedding ──→ 余弦相似度 ──┘
```

**优点：**
- BM25 保底：精确命中不丢分，高频术语优先
- 向量补语义：同义召回不丢人
- 两者互补，单一方案的缺陷被另一方覆盖
- 加权系数可调（benchmark/run_rag.py 全扫描，召回优先取 0.7 BM25 + 0.3 向量）

**代价：**
- 多一个 embedding 模型依赖（~33MB 本地模型）
- 每次检索多一次向量编码（~10ms）
- 存储翻倍（多存 384 个 float 的向量）

---

## Embedding 模型选型

选了 **BAAI/bge-small-zh-v1.5**，不是更大的模型。

| 维度 | bge-small-zh | bge-base-zh | bge-large-zh |
|---|---|---|---|
| 向量维度 | 512 | 768 | 1024 |
| 模型大小 | ~33MB | ~130MB | ~330MB |
| 推理速度 | 快 | 中 | 慢 |
| 精度 | 够用 | 更好 | 最好 |

**为什么选 small：**
1. **数据量级匹配** — 单 session 的知识点不超过 200 条，384 维足够区分。维度继续增加对 top-3 检索精度几乎没有提升。
2. **速度** — 384 维的余弦相似度在 200 条数据上 < 1ms（numpy 暴力计算）
3. **部署成本** — ~33MB 模型加载到内存即可，不需要 GPU，不需要额外服务
4. **中文优化** — bge 系列在 MTEB 中文榜单上表现稳定，对 StudyForge 的八股文场景够用

---

## 为什么不上向量数据库

当前量级（< 200 条/ session）下，numpy 暴力计算余弦相似度 < 1ms。

| 方案 | 适用量级 | 运维成本 |
|---|---|---|
| numpy 暴力搜索 | < 10万条 | 零，无额外服务 |
| FAISS (IndexFlatIP) | < 1000万条 | 无服务，单机库 |
| Milvus / Qdrant | > 1000万条 | 需维护分布式服务 |

**结论：在数据量达到万级以前，上向量数据库属于过度设计。工具选型看数据量级，不为了用而用。**

---

## 为什么不做 re-rank

Re-rank（用交叉编码器对检索结果重排序）的收益在知识库 > 1000 条时明显。

- 当前数据量 ~200 条，top-3 检索精度已经足够
- 加 re-rank 多一次模型调用（cross-encoder，比 embedding 还慢），延迟翻倍
- 边际收益低：top-3 里如果混入一个不相关的，LLM 出题时会自动忽略

## 实现方案

### 存储

不引入新数据库，直接在 `knowledge_points` 表加字段：

```python
class KnowledgePoint(Base):
    __tablename__ = "knowledge_points"
    # ... 现有字段不变 ...
    embedding = Column(JSON, nullable=True)  # 384个float，存JSON数组
```

### 流程

```
导入资料时（planner）：
  提取知识点 → 对每个 KP 生成 embedding → 存入数据库

复习出题时（question_gen）：
  1. BM25 检索（现有逻辑不变）
  2. 向量检索（query = 当前 KP 内容）
  3. 加权融合（0.7 BM25 + 0.3 向量）
  4. 取融合分最高的 top-3

薄弱扩散时（_build_review_queue）：
  1. BM25 扩散（现有逻辑不变）
  2. 向量扩散（薄弱 KP → 语义相似的非薄弱 KPs）
  3. 去重合并
```

### 新增依赖

```
sentence-transformers    # embedding 模型加载
numpy                    # 余弦相似度计算（已有大概率已安装）
```

## 面试话术

### Q：为什么从 BM25 升级到混合检索？

> "项目初期知识点少（< 50 条），BM25 的关键词匹配够用了。随着数据量增长到 200+ 条，出现了一个问题：**同一个概念用户有多种问法**，比如 goroutine 调度、GMP 模型、协程管理，BM25 搜不到同义表达。
>
> 我们没有推翻 BM25 重做，而是做了 **Hybrid Search**：保留 BM25 的通路做精确匹配，叠加向量检索做语义扩展，加权融合后排序。BM25 是保底的——那些高频专有名词它搜得比向量好。向量是扩展的——它兜住了 BM25 搜不到的同义表达。"

### Q：为什么选 bge-small 不用大模型？

> "因为这个量级（200 条）384 维和 1024 维的 top-3 检索精度几乎没有差别。但 small 模型只有 33MB，加载在内存就能跑，不需要 GPU。**选型看量级，不是模型越大越好。**"

### Q：为什么不上向量数据库？

> "200 条数据上向量数据库，就像用集装箱运一个背包。numpy 暴力余弦 < 1ms，足够。等哪天 session 的知识点超过 10 万，再考虑 FAISS。"

### Q：Hybrid Search 的权重怎么调的？

> "早期用一个小验证集（人工标注 + NDCG@3）倾向于 0.3 BM25 + 0.7 向量。后来写了可复跑的评测 `benchmark/run_rag.py`（108 条查询 × 三路检索器 + bm25_weight 全扫描），发现**取决于优化目标**：排序质量优先选低 BM25 权重，召回优先（Hit@3）选 **0.7 BM25 + 0.3 向量**（0.963 vs 0.944，MRR@3 也更高）。生产按召回优先改成了 0.7。现在的结论有数据支撑，不是拍脑袋。"

### Q：万一 embedding 模型崩了怎么办？

> "BM25 通路完全保留。如果 sentence-transformers 加载失败或推理超时，retriever 会自动降级到纯 BM25。**混合检索的架构优势就是降级不降功能。**"

---

## 一句话总结

> **BM25 精确但不理解语义，纯向量理解语义但会误召。Hybrid Search 用加权融合各取所长，BM25 保底、向量扩展，数据量不到万级不上专用向量库——工具选型跟着数据量级走，不追新。**
