# 数据库并发连接策略分析

> 背景：FastAPI 并发请求下 pymysql 报 `Packet sequence number wrong` 错误。
> 根源：全局单连接被多线程并行使用，包序号错乱。
> 此文分析各种方案的优劣和取舍。

---

## 问题复现

```
前端 Promise.all → 并发 4 个 HTTP 请求
        │
        ▼
uvicorn 多线程同时处理
        │
        ▼
4 个线程同时操作全局 db = SessionLocal()
        │
        ▼
pymysql 单连接收到乱序包
        │
        ▼
Packet sequence number wrong → 500
```

---

## 方案对比

### 方案 A：加锁（你猜的路径）

```python
lock = threading.Lock()

def get_stats():
    with lock:
        db.query(...)
        db.query(...)
        return result
```

**优点：**
- 改动最小，一行 `with lock` 就解决
- 逻辑简单，容易理解
- 不需要改已有的 `db.xxx()` 调用方式

**问题：**
- **串行化所有数据库操作**。4 个请求同时到，3 个在等锁。一个查询 ~10ms，4 个串行就是 40ms——请求量上来后线性恶化。
- 锁的范围难控制。如果每个端点都加锁，锁的颗粒度是整个请求处理周期（含 LLM 调用），那更夸张——`POST /api/review/start` 调一次 LLM 要几秒，后面所有请求都得排队等。
- 加锁只解决了同一个进程内的并发。如果将来 uvicorn 起多个 worker 进程（`--workers 4`），进程间的锁还得用分布式锁，复杂度爆炸。

```
请求 A ████████░░░░░░░░░░░░░░░░░░  10ms
请求 B ░░░░░░░░████████░░░░░░░░░░  10ms  ← 等 A 完才执行
请求 C ░░░░░░░░░░░░░░████████░░░░  10ms  ← 等 B 完才执行
请求 D ░░░░░░░░░░░░░░░░░░░░██████  10ms  ← 等 C 完才执行
总耗时：40ms（串行）
```

**结论：能解决问题，但上限低。单连接是瓶颈，锁只是把瓶颈显式化了。**

---

### 方案 B：连接池 + 每线程独立连接（scoped_session ✅）

```python
SessionLocal = sessionmaker(bind=engine)
db = scoped_session(SessionLocal)
```

`scoped_session` 的原理：

```
线程 A 首次调 db.query() → scoped_session 发现"线程 A 没有 session" → 新建 Session A → 从连接池拿连接 1
线程 B 首次调 db.query() → scoped_session 发现"线程 B 没有 session" → 新建 Session B → 从连接池拿连接 2
线程 A 再次调 db.query() → scoped_session 发现"线程 A 已有 Session A" → 复用连接 1
```

**优点：**
- **真正的并行**。N 个请求同时处理，N 个连接同时工作
- **不需要锁**。每个线程有自己的 session，天然隔离
- **连接池复用**。`pool_size=5` 控制最大连接数，不会把 MySQL 打死
- `pool_pre_ping=True` 在取连接前 ping 一下，自动丢弃断开的连接

```
请求 A ████████████████████████████  10ms
请求 B ████████████████████████████  10ms  ← 和 A 同时执行
请求 C ████████████████████████████  10ms  ← 和 A 同时执行
请求 D ████████████████████████████  10ms  ← 和 A 同时执行
总耗时：10ms（并行）
```

**代价：**
- 每个线程多一个数据库连接（内存开销极小，~几百 KB）
- 请求结束后 session 不会自动销毁（要手动 `remove()` 或等 GC）
  - 但 scoped_session 的 session 在线程结束后会被垃圾回收
  - 对短请求来说，GC 回收速度足够

---

### 方案 C：请求级 session（FastAPI Depends 模式）

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@router.get("/api/stats")
def get_stats(db: Session = Depends(get_db)):
    db.query(...)
```

**优点：**
- 最正统的做法。每个请求拿一个 session，请求结束自动关闭
- 连接归还到连接池，没有泄漏风险
- 大厂项目的标准模式

**问题：**
- **改动量大**。所有 `storage/db.py` 里 `db.xxx()` 的调用都要改成依赖注入参数
- **LangGraph 图节点不兼容**。`graph/node.py` 里的 `scheduler`、`judge` 等节点函数直接 `from storage.db import db`，它们不是 FastAPI 路由，拿不到 `Depends(get_db)`
- **两套 session 管理**。API 路由用 `Depends`，图节点用全局 `db`，增加了心智负担

**结论：大项目或新项目首选，但 StudyForge 这种已有大量直接 `import db` 代码的项目改造成本高。**

---

## 选型矩阵

| 维度 | 加锁（A） | scoped_session（B） | Depends（C） |
|---|---|---|---|
| 改动量 | 极小 | 1 行 | 大规模 |
| 并发性能 | ❌ 串行 | ✅ 并行 | ✅ 并行 |
| 扩展性（多进程） | ❌ 需分布式锁 | ✅ 天然适配 | ✅ 天然适配 |
| 代码侵入 | 无 | 极小（import 语意不变） | 大（改所有路由签名） |
| 兼容现有 graph/ 模块 | ✅ | ✅ | ❌ 两套 session |
| 连接泄漏风险 | 低 | 低 | 最低 |
| 面试能讲什么 | "我用锁解决" | "连接池隔离连接" | "依赖注入管理资源" |

---

## 结论

**选 B（scoped_session）**，理由：

1. **性能最好** — 真正并行，不加锁不串行
2. **改动最小** — 把 `db = SessionLocal()` 改成 `db = scoped_session(SessionLocal)`，一行代码，所有 `db.xxx()` 调用不改
3. **兼容现有代码** — graph/ 模块里的 `from storage.db import db` 完全不用动
4. **上限高** — 多 worker 多进程下 scoped_session 仍然正确
5. **面试能说清楚** — "连接池隔离 vs 锁串行"这个选型本身就有工程深度

加锁看起来简单，但它其实是**用性能下降换正确性**。而连接池方案既正确又并行，没有牺牲任何东西。
